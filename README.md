# Growth Experiment Lab

一个 A/B 实验的**决策模拟器**。不是算个 p 值就完，而是把增长 PM 每天要做的三个判断做成能上手操作的工具：**样本量够不够、什么时候能停、这个提升值不值得全量。**

- **在线 Demo**：https://andyzhang666666.github.io/growth-experiment-lab/ （四个页签：实验设计器 / 偷看惩罚模拟器 / 结果解读器 / 实验记录）
- **姊妹项目**：[creative-eval](https://github.com/AndyZhang666666/creative-eval) —— 那套是「AI 做出来的东西怎么证明它好不好」，这套是「改动做出来了怎么证明它真的有用」，都是同一个问题的不同面
- 全部计算在浏览器本地跑完，不上传任何数据

## 它解决什么问题

我在美团做促销效率优化时，对优惠券梯度做 A/B 验证，最难的不是跑实验，是三件事：

**实验前算不清要多少样本。** 公式网上一搜就有，但你不知道「想检出 0.5 个点的提升」意味着要跑小半年。要有个东西让你看见「MDE 砍一半，样本量翻两番」那条曲线有多陡。

**跑到一半看到数字好看，想提前停。** 忍住是对的，但没人说得清「偷看」的代价到底是多少。所以这个工具用蒙特卡洛真跑一遍给你看：两组真实转化率完全一样的前提下，每天偷看一显著就停，假阳性率会从 5% 飙到 **22.45%**（见下面「校验」）。

**跑完了提升 2 个点，老板问这 2 个点值多少钱、置信不置信。** 市面上的显著性计算器只回答「显不显著」，不回答「用区间下界算最保守能拿多少」。

这三件事没有一个是纯统计问题，都是「统计结论怎么变成今天的动作」的问题。

## 核心逻辑与假设

### 只用了两个检验

**两比例 z 检验**（合并方差，检验两组转化率是否相同）：

```
z = (p₂ - p₁) / √( p̄(1-p̄)(1/n₁ + 1/n₂) )      p̄ = (x₁+x₂)/(n₁+n₂)
```

**样本量公式**（教科书形式，每组）：

```
n = (z_{1-α/2} + z_{1-β})² · [ p₁(1-p₁) + p₂(1-p₂) ] / (p₂ - p₁)²
```

不等分组时 treatment 的样本量是 control 的 k = ratio/(1-ratio) 倍，方差项相应缩放。

**这里有个要说明的地方**：Evan Miller 的样本量计算器用的是
`n = (z_{1-α/2}·√(2p̄(1-p̄)) + z_{1-β}·√(p₁(1-p₁)+p₂(1-p₂)))² / δ²`，
对零假设下方差的估法不同。他的页面默认例子（20% 基线、+5 绝对提升）给 1030，本项目的公式给 1091，差 6%。**两个都对** —— 差别来自「H₀ 下方差怎么估」这个假设，不是谁算错了。本项目选教科书形式，因为它能对着手算，也更容易和别的文献对照。`scripts/test-stats.mjs` 里两个公式都做了对照。

### 置信区间用 Newcombe，不用 Wald

两比例之差的 95% 区间用 **Newcombe (1998) 方法 10** —— 由两个 Wilson 单比例区间拼出来，而不是教科书常见的 Wald 正态近似。

理由：增长 PM 经常碰到转化率 5% 以下、样本不到 1000 的场景。Wald 在这种边界下会给出荒谬结果（x=0 时区间宽度变成 0，或者下界跑到 -1 以下）。Wilson/Newcombe 在小样本和极端比例下仍然稳。大样本时两者几乎一样，没有代价。选择理由写在 `docs/DECISIONS.md`。

### 偷看惩罚的模拟设计

- A/B 两组**真实转化率设成完全一样**（默认都是 10%），也就是真实效果为零 —— 任何「显著」都是假阳性
- 每次实验跑 T 天，每天每组各进固定人数，累计后做检验
- 对比四种策略：

| 策略 | 规则 |
|---|---|
| 只看一次 | 只在第 T 天检验一次，固定样本量检验 |
| 每天偷看 | 每天检验，一显著（p < α）就停 |
| O'Brien-Fleming 近似 | 第 k 次检查用边界 c·√(K/k)，c = 2.0，早期门槛极高、临近结束回落到 c |
| Bonferroni | 每次检查用 z_{1-α/(2K)}，K 是检查次数 |

随机数用 **mulberry32**，种子写死在脚本和页面默认值里（`20260913`），所以 README 里的数字你本地跑一遍会得到一模一样的结果。

**已知近似**：真正的 OBF 常数要解多元正态积分，没有解析形式，这里取 c = 2.0。所以模拟出的 OBF 假阳性率是 6.60% 而不是精确的 5.00%。要压到精确 5%，c 得数值求解到约 1.977。

## 三个关键产品决策

**一、把「偷看惩罚」做成主角，而不是塞在文档里的一句话。**

讲实验设计的材料都会说「不要偷看」，但都是一句带过。没有任何体感。我把它做成一整页可交互的模拟器，让人自己调参数看假阳性率怎么涨 —— 用一个能亲手跑出来的 22.45% 去说服人，比写十遍「不要偷看」有用。

**二、不显著的时候，给出「继续跑」和「关掉」两个不同结论。**

大多数计算器碰到 p > 0.05 只会说「不显著」。但「不显著」有两层完全不同的意思：**还没跑够**（效应是真的，样本不够）和**效应本来就小**（再跑也检不出）。判据是成本：按现在观测到的效应量算，达到 80% power 需要多少样本 —— 不超过现在的 3 倍就继续跑，否则关掉。这个 3 倍是判断不是计算，写在 `docs/DECISIONS.md` 里。

**三、业务换算用区间上下界，不用点估计。**

「提升 2 个点，月流量 15 万，单次价值 30 元 → 月增 9 万」这个算法是错的，因为它拿点估计当确定值。实际应该是「最保守也有 X，最好情况到 Y」。决定要不要全量，看 X（置信区间下界），不看那个好看的点估计。这一条在页面上是显式的，不是注释里的小字。

## 什么失败了，怎么修的

**一、Bonferroni 边界我先用了近似式，跑出来的假阳性率低得离谱。**

第一版 `lib/peeking.js` 里我偷懒，用 `√(2·ln(2K/α))` 近似 Bonferroni 分位数，注释还写「和精确值差 0.01%」。加进共享模块重跑之后，Bonferroni 那档给出 **0.40%** —— 比 α 低了一个数量级，等于「保守到荒谬」。

回去核对：`√(2·ln(2K/α))` 是 Mills ratio 的一阶近似，K=14 时给 2.9137，看着没错；但它对 α 的敏感度被放大了，而且我当时手算的对照值本身就取错了。真正干净的做法是直接用 `lib/stats.js` 里已经用标准正态表校验过的 `normalQuantile(1 - α/(2K))`。改完重跑，Bonferroni 给 **2.30%** —— 仍然保守（本来就该保守），但落在合理范围。

教训：**已经有校验过的实现，就不要在第二个地方重新近似一遍。** 现在 `lib/peeking.js` 直接从 `lib/stats.js` 导入 `obfBoundary` 和 `bonferroniBoundary`，全项目只有一处边界公式。

**二、统计测试里两个 case 卡在浮点精度上，我一开始的容忍度定得没道理。**

`z_{0.001}` 期望 -3.090232，实现给 -3.090253，差 2.1e-5，我却把容忍度定成 1e-5，于是 FAIL。另一处「两组完全相同时 p = 1」期望严格等于 1，实现给 0.999999999 —— 这是浮点运算的必然结果，不是 bug。

修法不是放松标准了事，而是分开看：前者的误差来自 Acklam 反函数逼近（相对误差 ~1e-9 说的是相对量级，在 z≈3 处绝对值就是 1e-5 量级），把容忍度改成 5e-5 并注明原因是对的；后者把断言改成「p ≈ 1」并注明「浮点精度限制」，因为数学上它就该是 1，是浮点数做不到。**把「实现错了」和「浮点数就这样」分开，比统一调宽容忍度诚实。**

**三、MDE 曲线的红点大部分时候画不出来。**

第一版 `Designer.js` 里 MDE 曲线用的 Recharts 默认分类轴，横轴按 0.5% 的步长取点，红点只在当前 MDE 恰好落在这些点上时才渲染。意味着你把 MDE 拖到 3.2% 就看不见自己在曲线哪一段了 —— 而「看见自己站在哪」正是画这条曲线的全部意义。

修法是把 X 轴改成 `type="number"`，曲线按当前 MDE 动态取 20 个点（保证红点一定在视野里），`ReferenceDot` 就能画在任意位置。

### 2. 偷看惩罚模拟 —— `results/peeking-sim.json`

配置：种子 20260913，N = 2000 次，T = 14 天，每天每组 500 人，两组真实转化率均为 10%（零效应），α = 0.05。

| 策略 | 假阳性率 | 是 α 的几倍 | 提前停止次数 |
|---|---|---|---|
| 只在结束时看一次 | **4.95%** | 1.0× | — |
| 每天偷看，一显著就停 | **22.45%** | **4.5×** | 449 / 2000 |
| O'Brien-Fleming 近似边界 | **6.60%** | 1.3× | 132 / 2000 |
| Bonferroni 分摊 | **2.30%** | 0.5× | 46 / 2000 |

**这个 22.45% 怎么来的**：2000 次实验里，有 449 次在 14 天中间就撞出一个 p < 0.05 然后停了 —— 而两组真实效果为零，所以这 449 次全是假阳性。

**停止日的分布比总数更值得看**（`results/peeking-sim.json` 里的 `stopDayDistribution`）：

| 停止日 | D1 | D2 | D3 | D4–D7 | D8–D14 |
|---|---|---|---|---|---|
| 次数 | 94 | 68 | 57 | 136 | 94 |

**前三天就停掉的占 219/449 = 49%。** 这是偷看最阴的地方：实验前几天数据量小、噪声大，最容易偶然撞出显著性。你以为「效果很明显，第一天就见效」，实际上你只是抓到了噪声最大的那个时刻。停得越早，结论越不可信。

O'Brien-Fleming 把假阳性压回 6.60%（近似边界的代价，见上），Bonferroni 压到 2.30% —— 保守过头，代价是漏检（power 下降），这也是个真实的取舍，不是越保守越好。

```bash
npm run sim:peeking
```

### 3. Power 校验 —— `results/power-check.json`

前两个脚本验的是「公式算得对不对」，这个验的是「公式给的样本量真能检出吗」。

参数：baseline = 8%，绝对 MDE = 2 个点，α = 0.05，目标 power = 0.8。
公式给每组 **3211** 人。然后真去模拟 1000 次（这次 A 组 8%、B 组 10%，**是有效应**的），数有多少次检出：

**实际检出率 81.1%**，与理论 80% 差 1.1 个点，在 3 个点的容忍范围内 **通过**。

```bash
npm run sim:power
```

如果模拟出的 power 和理论值差超过 3 个点，说明样本量公式或检验实现有问题 —— 这个脚本就是拿来拦这种错误的。

## 已知局限与下一步

- **OBF 边界是近似**：c 取 2.0，模拟出的假阳性率 6.60% 而非精确 5%。下一步应该数值求解 c 使假阳性率精确等于 α，或者实现真正的 Lan-DeMets alpha spending 函数。
- **只做固定期限检验**：没做「连续监测 + 自适应样本量重估」。真实平台（Optimizely、字节的实验平台）会在中期重估样本量，这需要 alpha spending 更完整的实现。
- **没做分层与方差缩减**：任何真实场景都需要 CUPED 之类的方差缩减（用实验前数据当协变量），能把所需样本量砍掉 30-50%。没做，所以本工具算出的样本量是偏保守的。
- **假设无用户重复**：模拟用 binomial 抽样，隐含「每个用户只出现一次」。真实场景有重复访问，需要用户级聚类方差，实际有效样本量比名义值小。
- **合成数据不是真实业务数据**：`data/experiments.json` 里 10 条实验全部是合成的，场景虚构（新人优惠券、结算按钮、推送时机等），用 `scripts/gen-experiments.mjs` 以固定种子生成。生成规则见 `data/GENERATION.md`。
- **不做贝叶斯**：全程频率学派。贝叶斯在「treatment 优于 control 的概率是多少」这个问法上更直观，但引入先验会让 PM 问「这个先验哪来的」，增加解释负担。真要做得另开一个项目，不要混两套范式。
